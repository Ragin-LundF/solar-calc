# Testing Instructions

Load this file for any test work and for any behavior change — behavior changes without test changes are incomplete by definition.

Related procedures: `../harness/test-generation-harness.md` (how to build a suite), `../harness/no-cheating-test-harness.md` (what disqualifies a test), `../harness/rest-api-test-harness.md` (REST scenario matrix).

## Mandatory principles

- High test coverage is mandatory for new and changed code — as a byproduct of asserting behavior, never as the goal itself.
- Tests verify behavior, not line execution.
- Every behavior change requires new or updated tests in the same change.
- Never weaken, delete, skip, or rewrite tests just to make a change pass.
- Never change production code solely to satisfy a brittle or artificial test, unless the behavior change is genuinely required.
- Test public behavior, not implementation details, whenever public behavior is testable.
- Small, focused tests with behavior-describing names.

## Unit tests

- Use `kotlin.test` annotations and assertions when possible.
- Use named arguments in assertions: `assertEquals(expected = expectedValue, actual = actualValue)`.
- Test functions and parameter behavior directly.
- Cover: positive paths, negative paths, edge cases, boundary values, nullability where `null` is valid, and error paths.
- Assert exact exception types; assert messages only when the message is part of the contract.
- Fixtures/builders reduce noise, but scenario-relevant inputs stay visible in the test.

## REST API tests

- REST APIs are tested through Cucumber/Gherkin scenarios (via the BBD Cucumber Gherkin library approach when available) — see `rest-api-cucumber.md`.
- REST behavior tests exercise the HTTP boundary: bodies, status codes, headers, validation errors, security, paging, sorting, and compatibility.
- Controller-only unit tests are **not** a substitute for REST scenarios. They may exist in addition, never instead.

## Coverage expectations

- New domain logic: near-complete branch coverage.
- Critical business logic, validation, security checks, and error mapping: explicit positive *and* negative tests, always.
- Generated code: no direct unit tests unless custom behavior wraps it.
- Mapping code: tested whenever it contains conditions, transformations, defaults, or compatibility behavior. Pure field-copy mappings generated by tooling do not need tests.
- Never chase coverage with meaningless tests. Either add meaningful assertions or leave generated/trivial code excluded per project policy.

## Anti-cheating rules

Never do the following (see `no-cheating-test-harness.md` for the full gate):

- Assert only non-null when the exact value is known.
- Mock the class or function under test instead of its dependencies.
- Re-implement production logic inside the test to compute expected values.
- Use broad `any()` matchers for values that carry the behavior under test.
- Use `Thread.sleep` to make timing-dependent tests pass.
- Add `@Disabled`, `ignore`, assumptions, or conditional returns to dodge failing scenarios.
- Delete negative tests for validation, security, or error cases.
- Replace integration tests with mocked unit tests without equivalent coverage.
- Reduce assertions after an implementation change without justifying the behavior change.

## Test naming

Behavior-focused names that read as specifications:

- `returns report when request is valid`
- `rejects missing bearer token`
- `maps expired consent to unprocessable entity`
- `keeps optional openapi field nullable`

Never name a test after the method it calls (`testGetUser`) — name it after the behavior it protects.

## Completion criteria

A change is complete only when all of the following hold:

1. Unit tests cover the changed function behavior and parameters.
2. REST behavior is covered by Cucumber scenarios where REST was touched.
3. Negative, edge, and error paths are covered.
4. Each test would fail without the production change or under a realistic regression.
5. Static analysis and formatting checks pass.

Report the actual test results; if tests were not run, state the exact commands that must be run.
